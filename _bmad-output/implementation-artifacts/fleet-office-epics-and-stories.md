# 车队作战台 Epics and Stories

## Overview

本文件把完整工作台拆为十个按用户结果组织的 Epic，并以 V1/V1.5/V2 分期。每个 Story 可由一个开发代理在已有前序 Story 基础上独立完成，不依赖未来 Story。精确工期需在 Sprint Planning 根据团队与基础设施评估。

## Requirements Inventory

### Functional Requirements

- FR-001 今日工作流；FR-002 全局命令面板；FR-003 持续上下文。
- FR-004 对象目录；FR-005 人车关系；FR-006 事实视图。
- FR-007 派车工作；FR-008 派车校验与同步；FR-009 在途时间线。
- FR-010 风险收件箱；FR-011 处置任务；FR-012 证据查看。
- FR-013 一车一档；FR-014 到期与维护工作。
- FR-015 G7 适配与降级；FR-016 数据交换；FR-017 权限与审计。
- FR-018 Agent 工作线程；FR-019 证据计划与账本；FR-020 Context Pack 与策略。
- FR-021 工具注册与分层；FR-022 计划/进度/失败恢复；FR-023 风险分级审批。
- FR-024 并行专家与合并；FR-025 写后验证与刷新；FR-026 运行评估与交接。
- FR-027..FR-031 订单接入、履约、ETA、异常影响与凭证。
- FR-032..FR-036 运力池、候选、场景、批处理与预警。
- FR-037..FR-042 客户 SLA、沟通、案件、费用、对账与服务摘要。
- FR-043..FR-049 Playbook、知识、Agent/Skill 目录与评估门禁。
- FR-050..FR-056 语义指标、根因、预测、盈利、日报、优化闭环与 AI 成本。

### Non-Functional Requirements

- NFR-001 性能/新鲜度；NFR-002 可用性/降级；NFR-003 安全/隐私。
- NFR-004 一致性/幂等；NFR-005 可观测性；NFR-006 可访问性/兼容性。
- NFR-007 数据生命周期；NFR-008 容量/配额；NFR-009 Agent 安全/边界。
- NFR-010 Agent 可验证性；NFR-011 Agent 性能/成本；NFR-012 Agent 连续性。
- NFR-013..NFR-020 业务域一致性、异步性能、AI 可组合性、自动化安全、知识新鲜度、经营可重现、跨角色协作和 AI 数据治理。

### Additional Architecture Requirements

- 服务端 G7 反腐层是唯一外部入口，浏览器不得接触 G7 凭据。
- PostgreSQL 事务 Outbox 驱动读模型与外部同步；Consumer 至少一次处理并幂等。
- 业务状态与 G7 同步状态正交；外部失败保留本地工作和最后成功事实。
- 每个仓储/API 强制 TenantScope，应用授权与 PostgreSQL RLS 双层隔离。
- 只有 G7 released 接口可成为 V1 验收硬依赖；行程分段置于关闭的特性开关后。
- 读模型可从写模型/Outbox 重建；Redis Streams 不作为唯一真相。
- Agent 只能调用注册工具，模型上下文受 TenantScope 和 Context Pack 限制；G7 凭据永不进入模型上下文。
- Agent 线程/运行事件/证据/审批/回读追加写入，R2/R3 未经批准不得执行；写成功后必须回读确认。

### UX Design Requirements

- UX-001 实现稳定工作空间与键盘可操作的活动流。
- UX-002 实现按对象/工作/命令分组的命令面板，写操作不绕过确认。
- UX-003 实现可深链接恢复的对象上下文抽屉。
- UX-004 实现可比较候选与冲突说明的派车编排器。
- UX-005 实现事实不可编辑、高风险需复核的风险处置器。
- UX-006 实现新鲜/延迟/失联/未知四态数据脉冲。
- UX-007 实现紧凑对象表格、选择后批量动作与导入预检。
- UX-008 实现带阶段和恢复入口的 Agent 运行线程。
- UX-009 实现证据账本、事实/推断/未知分层和来源新鲜度。
- UX-010 实现 R2/R3 批准栏与写后回读状态。
- UX-011 实现并行专家活动和冲突合并。
- UX-012 实现班次交接摘要与线程恢复。
- UX-013..UX-022 实现完整工作台壳、晨间简报、订单履约、运力场景、影响图、客户沟通、结算调查、Playbook、知识引用和 AI 控制台。

## Epic List

### EP-001：可信地看见并接手今天的工作

授权用户能在正确租户与数据范围内查看 G7 对象/事实，通过工作流、命令面板和上下文抽屉快速理解变化并接手工作。

**FRs covered:** FR-001, FR-002, FR-003, FR-004, FR-006, FR-015, FR-017

### EP-002：完成派车并持续跟进在途

调度员能建立派车任务、避免人车冲突、同步 G7 绑定，并在一条时间线上跟进运行与同步异常。

**FRs covered:** FR-005, FR-007, FR-008, FR-009

### EP-003：把安全事件变成可审计的处置闭环

安全员能从增量事件中识别优先级、接手干预、查看证据，并通过复核关闭高风险事件。

**FRs covered:** FR-010, FR-011, FR-012

### EP-004：保持车辆合规且可用

车务人员能查看一车一档、处理证照/维护到期；管理员能可靠导入导出并执行受审计的数据治理。

**FRs covered:** FR-013, FR-014, FR-016

### EP-005：让 AI 成为受控的调度同事

运营用户能在对象和工作流上下文中创建可恢复的 Agent 线程；Agent 先检索有来源的事实，再给出可比较方案；所有外部副作用经过风险审批、写后回读和审计。

**FRs covered:** FR-018..FR-026; **NFRs covered:** NFR-009..NFR-012

### EP-006：让订单从接入到签收可持续履约

客服、调度和运营能把订单转成可执行履约计划，持续发现 ETA/承诺风险、理解异常影响并以凭证结案。

**FRs covered:** FR-027..FR-031; **UX:** UX-014, UX-015, UX-017

### EP-007：用场景规划运力并生成可控派车

调度与经理能看见未来运力、解释候选约束、比较 what-if，并从选中场景生成受控派车草稿。

**FRs covered:** FR-032..FR-036; **UX:** UX-016

### EP-008：闭环客户协同、案件和结算差异

客服、运营和财务能基于 SLA 主动沟通、处理索赔、匹配费用并调查结算差异。

**FRs covered:** FR-037..FR-042; **UX:** UX-018, UX-019

### EP-009：把知识、自动化和 AI 运行纳入治理

管理员能用受控工具构建 Playbook，管理知识和 Agent/Skill 版本，并用评估集阻止不合格版本发布。

**FRs covered:** FR-043..FR-049; **UX:** UX-020..UX-022

### EP-010：从经营指标走到可验证改善

管理层能使用统一口径发现根因、预测容量、理解盈利，把建议转为可跟踪改善并治理 AI 成本。

**FRs covered:** FR-050..FR-056; **UX:** UX-014, UX-022

### EP-011：让六类角色在同一底座上完成各自工作

物流老板、车队长、运营管理者、物流专员、调度和司机使用适合各自任务的工作面，同时共享对象、事实、权限和审计底座。

**FRs covered:** FR-057..FR-068; **UX:** UX-023..UX-031

### EP-012：让车辆从可见变成可运营

车队长、安全员和车务人员能把资产、实时健康、司机检查、缺陷、维修、油能、合规和成本连成闭环，并让车辆状态实时影响运输计划与客户承诺。

**FRs covered:** FR-069..FR-082; **UX:** UX-032..UX-040

## EP-001：可信地看见并接手今天的工作

### Story 1.1 / US-001：在正确租户和权限范围进入工作台

As a 车队运营用户，
I want 只进入我的租户、角色和组织/标签数据范围，
So that 我能安全地处理被授权的车队工作。

**Requirements:** FR-017, NFR-003, NFR-005, NFR-007

**Acceptance Criteria:**

**Given** 用户具有有效会话和一个租户内的角色/数据范围
**When** 用户打开任一工作空间或对象深链接
**Then** API 从会话派生 TenantScope，并只返回范围内数据
**And** 忽略浏览器提交的 tenant_id，记录 request/trace ID（TEST-001）

**Given** 用户没有对象权限
**When** 其通过 URL、搜索词或批量 ID 请求对象
**Then** 返回统一的不可访问结果，不泄露对象名称、车牌或计数
**And** 敏感拒绝事件写入审计（TEST-002）

**Given** 管理员变更角色或撤销会话
**When** 用户发起下一次请求
**Then** 新权限立即生效，旧会话不可继续提升访问（TEST-003）

### Story 1.2 / US-002：同步并检索车队对象目录

As a 车队经理，
I want 检索车辆、司机和场站的统一目录，
So that 我不必知道对象来自哪个 G7 菜单。

**Requirements:** FR-004, FR-015, UX-007, NFR-004

**Acceptance Criteria:**

**Given** 已配置合法 G7 测试租户
**When** 后台同步或用户按需刷新车辆/司机/地址
**Then** 仅由服务端适配层签名请求，并按来源 ID/外部 ID 幂等写入镜像
**And** 保存组织、标签、属性、版本和最后同步时间（TEST-004）

**Given** 用户按车牌、司机姓名或外部 ID 搜索
**When** 查询完成
**Then** 在 10,000 车辆假设数据集下返回权限过滤、分页的紧凑列表
**And** 结果可直接打开对象深链接（TEST-005）

**Given** G7 返回冲突、权限或校验错误
**When** 同步结束
**Then** 错误被映射为内部分类，不覆盖最后成功镜像
**And** 可重试性与 upstream reference 可供管理员查看（TEST-006）

### Story 1.3 / US-003：查看带新鲜度的车辆事实

As a 调度员，
I want 查看车辆位置、速度和车况的来源与新鲜度，
So that 我不会把过期或未知数据当成实时正常。

**Requirements:** FR-006, FR-015, UX-006, NFR-001, NFR-002

**Acceptance Criteria:**

**Given** 车辆存在 GPS/状态快照
**When** 用户打开车辆上下文
**Then** 展示发生时间、接收时间、来源和新鲜/延迟/失联/未知之一
**And** 状态同时使用文本、图标和颜色（TEST-007）

**Given** 用户请求不超过 31 天的位置历史
**When** G7 返回游标分页
**Then** 服务端保持游标不透明并按配额加载
**And** 超过范围时在发出外部请求前给出可行动错误（TEST-008）

**Given** G7 超时或不可用
**When** 用户查看车辆
**Then** 显示最后成功事实、其时间和受影响能力
**And** 本地工作仍可查看和记录（TEST-009）

### Story 1.4 / US-004：从今天的工作流接手一项变化

As a 车队经理，
I want 在同一工作面搜索、理解并接手异常，
So that 我能用很少的操作开始处置。

**Requirements:** FR-001, FR-002, FR-003, UX-001, UX-002, UX-003, NFR-001, NFR-006

**Acceptance Criteria:**

**Given** 用户进入“今天”工作空间
**When** 工作流加载
**Then** 按风险、SLA 和角色返回活动记录，首个可用内容 p95 目标不超过 2 秒
**And** 每条记录包含对象、原因、时间、新鲜度、责任和一个主动作（TEST-010）

**Given** 用户按 `Ctrl/Cmd + K` 并输入车牌或动作
**When** 搜索返回
**Then** 在 p95 500ms 目标内按对象/工作/命令分组，支持键盘选择
**And** 写命令只打开预填编排器，不直接执行（TEST-011）

**Given** 用户选择活动并接手
**When** 操作成功
**Then** 右侧上下文原地更新，工作流进入处理中且 URL 可恢复选择
**And** 全流程可用键盘完成并具有可见焦点（TEST-012）

## EP-002：完成派车并持续跟进在途

### Story 2.1 / US-005：创建派车草稿并比较候选

As a 调度员，
I want 创建派车任务并比较车辆/司机候选，
So that 我能基于计划和可信事实选择运力。

**Requirements:** FR-007, UX-004

**Acceptance Criteria:**

**Given** 用户从命令面板或待派工作进入
**When** 输入业务单号、场站/线路和计划时间
**Then** 可保存派车草稿，状态为 DRAFT，不触发 G7 写入（TEST-013）

**Given** 草稿信息完整
**When** 打开候选比较
**Then** 车辆/司机行分别显示组织范围、资格、冲突、新鲜度和可用性
**And** 阻塞与建议使用不同语义，建议可覆盖并记录理由（TEST-014）

### Story 2.2 / US-006：校验人车关系并确认派车

As a 调度员，
I want 在确认前发现时间和资格冲突，
So that 不会生成不可执行的人车安排。

**Requirements:** FR-005, FR-008, NFR-004

**Acceptance Criteria:**

**Given** 同一司机在时间段内已有另一车辆绑定
**When** 用户尝试确认派车
**Then** 确认被阻止并显示冲突对象/时间，未经重新选择不可继续（TEST-015）

**Given** 结束时间不晚于开始时间或同车同身份重叠
**When** 执行确认
**Then** 本地校验与数据库约束均拒绝命令，且不会发送 G7 请求（TEST-016）

**Given** 派车通过校验
**When** 用户确认
**Then** 本地状态原子变为 CONFIRMED，并写入幂等 G7 绑定命令
**And** 重复提交相同 Idempotency-Key 只返回原结果（TEST-017）

### Story 2.3 / US-007：在一条时间线跟进在途变化

As a 调度员，
I want 将计划、围栏、位置、事件和备注放在同一时间线，
So that 我能理解运行偏差并立即创建工作。

**Requirements:** FR-009, UX-003

**Acceptance Criteria:**

**Given** 派车任务已确认
**When** 围栏进出和位置事实到达
**Then** 时间线按发生时间展示来源、接收时间和计划节点
**And** 乱序到达不会覆盖较新的事实（TEST-018）

**Given** 用户选择延误或异常节点
**When** 创建工作并设置责任/时限
**Then** 工作与派车、车辆、司机和来源事实关联，且出现在“今天”（TEST-019）

**Given** `trip-segment-search` 开关关闭
**When** 查看在途时间线
**Then** 仍由计划、位置历史和围栏记录完整工作，不调用 developing 接口（TEST-020）

### Story 2.4 / US-008：从 G7 同步失败中恢复

As a 调度员，
I want 看见并处理人车绑定同步失败，
So that 我不会重复派车或误以为外部已生效。

**Requirements:** FR-008, FR-015, NFR-002, NFR-005

**Acceptance Criteria:**

**Given** 本地派车已确认而 G7 暂时失败
**When** 适配器返回 retryable 错误
**Then** 业务状态保持 CONFIRMED，同步状态为 FAILED/RETRYING
**And** UI 显示最后尝试、影响和重试/撤销动作（TEST-021）

**Given** 用户或后台重试同一同步命令
**When** G7 成功或返回已有相同绑定
**Then** 状态收敛为 SYNCED，不产生重复绑定（TEST-022）

**Given** 同步积压最老项超过 30 分钟
**When** 监控规则触发
**Then** 生成管理员运营工作并携带 request/trace/upstream reference（TEST-023）

## EP-003：把安全事件变成可审计的处置闭环

### Story 3.1 / US-009：可靠接入并去重 G7 安全事件

As a 安全主管，
I want 系统持续接入且不重复创建安全事件，
So that 风险收件箱可信且可恢复。

**Requirements:** FR-010, FR-015, NFR-004, NFR-005

**Acceptance Criteria:**

**Given** 事件 Feed 返回游标、重复和乱序更新
**When** Worker 消费
**Then** 按租户、来源事件 ID 和 payload hash 幂等保存，游标只在成功处理后推进（TEST-024）

**Given** Feed 游标失效
**When** G7 返回游标错误
**Then** 暂停分区、记录缺口窗口、通过历史事件回补并恢复
**And** 缺口和恢复结果进入审计/指标（TEST-025）
